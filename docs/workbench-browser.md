# Ручной обход в браузере: приёмы и тихие отказы

Указатель на этот файл — в CLAUDE.md, раздел «Looking at the workbench».
**Открывать ДО первого замера, клика или снимка, а не когда что-то не сошлось.**
Это не справочник по инструменту, а список способов, которыми браузер отвечает
правдоподобно и неверно: почти каждый пункт здесь — вывод, который однажды был
сделан уверенно и оказался не про тот код.

Полный список приёмов и ловушек ручного обхода — промт mcp-note в каталоге
артефактов задач (см. `CLAUDE.local.md`), `promts/wb-browser-check`. Читать перед приёмкой
волны: там же рецепты замеров (наложения попарным пересечением, `grayscale(1)`
для «цвет не единственный носитель», обрезка через `clip*`) и сортировка
замечания на стенд / компонент / верстак.

## Граница: чей браузер

Manual looking, measuring and clicking go through the `claude-in-chrome` MCP —
the owner's chromium with his profile. His debugging scripts live there, and a
browser you launched yourself does not have them; two browsers also means two
answers to the same question, and no way to tell which one the owner is seeing.

The border is automation, not tooling. `smoke:wb` keeps its own headless
playwright and its own port 5275 on purpose (`scripts/smoke-workbench.mjs`
says why): a gate that attaches to the running server checks a tree that is
not necessarily HEAD. Gates get their own browser; eyes get chromium.

## Живость вкладки: порядок захода

**Вкладку агент СОЗДАЁТ САМ, но она рождается В ФОНЕ, и до подтверждённой
живости по ней не делается НИКАКИХ выводов** (правило переписано 17.09.2026 по
просьбе владельца; прежняя редакция запрещала создавать вкладку вовсе, и запрет
был лишним — работала не он, а проверка под ним).

Порядок такой.
1. `tabs_context_mcp {createIfEmpty: true}`, затем сразу `navigate` на страницу
   кадра: на `chrome://newtab` скрипт не выполняется, и `visibilityState` там
   прочесть нельзя вовсе.
2. Попросить владельца вывести окно вперёд и ДОЖДАТЬСЯ его слова. Своя вкладка
   передней не становится: если группа уже была, передней остаётся прежняя
   (DS-278, 14.09.2026 — заход целиком ушёл на спящую вкладку и вернул
   числа с запасной ширины 520); если группы не было, расширение открывает своё
   окно ЗА окном владельца (15.09.2026, приёмка пачек эпика 249 — ни снимков, ни
   ввода).
3. Снять живость СВОИМ наблюдателем и только потом мерить.

Живость — это не `visibilityState`. Читать надо три числа разом: свой
`ResizeObserver` обязан сработать (спящая вкладка их не доставляет и молчит об
этом), `setTimeout(300)` обязан прийти около 300 мс (у спящей 800–1000), и
`requestAnimationFrame` обязан доставляться. Замер живой вкладки 17.09.2026:
`fired 2`, `timerLag 301`, `raf 1`. Проверка «`viewBox` равен `innerWidth`»
ложноположительна на кадре шириной ровно 520 — совпадение с запасным числом она
от настоящей раскладки не отличает.

`hasFocus` при этом может остаться `false`: окно видимо, но клавиатурный фокус в
другом. Для замеров это неважно, для проверок ввода — важно, и тогда владельца
просят ещё и щёлкнуть по окну.

Если спячка всё же случилась, сработал один обход: грузить кадр ЗАНОВО на
нужной ширине (новый iframe), а не менять `f.style.width` у живого. На
монтировании Tabs и LineChart считают раскладку сами и отдают честные числа;
BarChart — нет, его холст остаётся на запасных 520. Цена: `setTimeout(120)`
приходит через ~999 мс, загрузка кадра ~480 мс, в один вызов влезает около
десяти ширин.

## Фоновая вкладка не доставляет `ResizeObserver` и `requestAnimationFrame`

**A background tab does not deliver `ResizeObserver` or `requestAnimationFrame`,
and says nothing about it.** An MCP tab is usually not the foreground one, so
layout-reactive code looks dead there: the observer never fires, the numbers
stay at their mount values and are internally consistent — a plausible reading
that is simply not about the running code. Caught on DS-126: a fresh
observer created inside that page fired 0 times while the element demonstrably
went 1338 → 227 → 1338. **Before believing that layout-reactive code is broken,
create your own observer in the page and check IT fires.** Zero means the tab
is asleep, not that the code is wrong.

## Та же фоновая вкладка врёт и на СНИМКЕ

**Та же фоновая вкладка ВРЁТ И НА СНИМКЕ, а не только на наблюдателях.** При
`document.visibilityState === 'hidden'` `computer screenshot`/`zoom` через раз
падает по таймауту CDP (30 с), а «удачный» снимок может вернуть МОЗАИКУ из
устаревшего фрагмента страницы — сетку одинаковых уголков рамок вместо кадра.
Поймано 14.09.2026 на DS-268: после навигации и `zoom:3` на документе
снимок пришёл без единой ошибки, и отличить его от настоящей отрисовки можно
было только глазом, знающим, что там должно быть. Повтор вызова лечит
таймаут, но не мозаику. **Перед обходом, где вывод делается по снимку, прочитай
`document.visibilityState`; `hidden` — попроси владельца вывести вкладку группы
MCP на передний план и не сворачивать до конца.** После этого та же серия
снимков прошла без единого сбоя.

## Спящая вкладка душит таймеры; CSS-раскладке ожидание не нужно

**Спящая вкладка душит таймеры до ~1 с, а CSS-раскладке ожидание не нужно
вовсе.** `setTimeout(180)` в фоновой вкладке пришёл через 802 мс, потом через
1000; цикл из восьми ширин с ожиданиями уронил `javascript_tool` по таймауту
CDP 45 с. Лечение: после смены `f.style.width` у видимого iframe прочитать
`f.offsetWidth` — это форсирует лэйаут синхронно, `@container` и медиазапросы
пересчитываются тут же, и развёртка по сотне ширин проходит одним вызовом.
Сверено на Pagination: числа без ожидания и после 180 мс совпали полностью
(приёмка DS-282, 14.09.2026). Ожидание остаётся нужным только семи
компонентам, где раскладку считает их JS через `ResizeObserver`. Заодно:
`textContent` ряда включает текст СКРЫТЫХ узлов (`display: none`) — видимый
текст сверяется по листовым узлам с ненулевой шириной, не по `textContent`.

## Дюжина случаев подряд — своим скрытым iframe

**Дюжину случаев подряд смотрят СВОИМ скрытым iframe, а не навигацией со
снимком на каждый.** Кадр — отдельный документ того же origin, что и оболочка
(`/frame.html?c=<Имя>&case=<id>&sid=1&theme=light`), поэтому из страницы
оболочки заводится зонд и крутится в цикле, а его `contentDocument` читается
напрямую:

```js
p = document.createElement('iframe'); p.id = '__probe'
p.style.cssText = 'position:fixed;left:-9999px;width:900px;height:600px'
document.body.appendChild(p)   // дальше p.src = … в цикле, ждать onload + ~60 мс
```

Порциями по ~15 загрузок на вызов: 55 подряд роняют `javascript_tool` по
таймауту CDP (45 с). Зонд убирать за собой. Живой пример утверждений, которые
так снимаются, — `scripts/case-states.mjs` (DS-134).

## Скрытый зонд врёт на ширине ТЕКСТА, примерно на 5 %

**СКРЫТЫЙ зонд врёт на ширине ТЕКСТА, примерно на 5 %, и `fonts.ready` этого не
лечит.** Один и тот же случай офскрин (`left:-9999px`) против видимого кадра:
`CommandBar/base` 611 против 642, `CommandBar/many` 1006 против 1060,
`SectionPanel--horizontal` 560 против 581. `GlobalSearch` совпал точно — его
ширина `calc(20rem * scale)` и от метрик текста не зависит, и вот это совпадение
части чисел и делает замер убедительным. Отсюда правило: **офскрин-зонд годится,
чтобы найти, ГДЕ смотреть; число в отчёт снимается с ВИДИМОГО кадра.**

## Видимый iframe заданной ширины — настоящий вьюпорт

**Видимый iframe заданной ширины — это настоящий вьюпорт, и это ПРЯМОЙ способ
посмотреть узкое.** Внутри него `innerWidth` равен заданной ширине, медиазапросы
срабатывают, `scrollWidth`/`clientWidth` честные, и настоящие клики и клавиши в
него долетают. Ширины в адресе КАДРА нет намеренно (`workbench/frame-url.ts`;
в адресе оболочки она есть — `w`, см. следующий раздел), а `resize_window`
меняет `outerWidth` и не меняет `innerWidth`, — то есть до DS-212 узкая
раскладка считалась проверяемой только косвенно. Считалась
зря. Ограничивать документ скриптом больше не нужно.

Оба факта — про 5 % и про вьюпорт — сняты браузерным агентом на слепом обходе
05.09.2026, а не выведены.

## «Смотрел на узком» — это ДВА разных сценария, и называть надо который

**Прямая загрузка узкого кадра и переход к нему с 768 — разные условия, и у
компонентов с JS-раскладкой они дают разные числа.** Оба верные. Приёмка
328/334 (19.09.2026): человек смотрел `EventCalendar/week` ПЕРЕХОДОМ 768 → 360
и получил порт на понедельнике (`scrollLeft` 0), браузерный агент — ПРЯМОЙ
ЗАГРУЗКОЙ 360 и получил порт на среде (`scrollLeft` 160). Расхождение нашлось
только потому, что человек ответил первым; промт, сказавший обоим «посмотри на
360», спросил их о РАЗНОМ и не знал об этом.

Решение (DS-345). Ширина живёт в адресе ОБОЛОЧКИ (`w`), и отсюда порядок:

- **Умолчание промта — ПРЯМАЯ ЗАГРУЗКА ссылкой**: `…&c=EventCalendar&case=week&w=440`.
  Она воспроизводима — это ссылка, — и ровно её естественно делает агент.
  Перечислять ширины без ссылок («ширины: 440, 768») больше нельзя: такая строка
  не называет сценарий вовсе.
- **ПЕРЕХОД заказывается ОТДЕЛЬНОЙ строкой** и только там, где предмет — сам
  перерасчёт при смене ширины: «открой на `w=768`, затем нажми чип 440 в группе
  „Ширина кадра“, число сними ПОСЛЕ». Это другой вопрос, и ответ на него
  сравнивается с прямой загрузкой, а не заменяет её.
- **Число в отчёте несёт способ**, как оно уже несёт `innerWidth` и
  `devicePixelRatio`: «440 прямой загрузкой» либо «440 переходом с 768». Без
  этого два верных ответа выглядят как один неверный.
- Расхождение прямой загрузки с переходом — **находка, а не шум**: компонент
  считает раскладку в JS и не пересчитывает её на `resize`. Заводить задачей.

Ширины в адресе КАДРА по-прежнему нет и не будет (`workbench/frame-url.ts`):
там она была бы обещанием вьюпорта, которого кадр не держит. `w` — поле
оболочки, и пишет его только `buildShellUrl`.

## Геометрию по осям — страницей развёртки

**Геометрию по осям — страницей развёртки, а не своим зондом** (DS-219).
`http://localhost:5274/sweep.html`, в ней `await __dsSweep.run({c, cases,
widths, scales, themes, targets, invariants})` — одна загрузка на случай,
ВИДИМЫЙ кадр, тема и шкала тем же `applyFrameEnv`, что у живого кадра, и
матрица одним ответом с нарушениями инвариантов (`min`, `grows`, `same`, `gt`
против `before`, `eq` против `preview`, `fits`, `hit`) и сводкой «N нарушений,
худшее — …». Живость вкладки проверяет сама (`live`), результат дублирует в
`__dsSweep.last` на случай таймаута CDP. Правила и отказы — в докблоке
`workbench/sweep.ts`. «Узла нет» в отчёте — нарушение, не пропуск: сначала
проверь, что цель вообще рисуется на этой ширине, а потом уже вини компонент.

## Зонд с доком не разговаривает, и это держится проверкой

Зонд с доком НЕ разговаривает, и это держится проверкой, а не аккуратностью.
Кадр говорит наверх широковещательно (`window.parent.postMessage`), а `sid=1`
в адресе зонда совпадает с номером первого настоящего кадра — так что ни
`origin`, ни `ns`, ни `sid` его не отличают. Отличает окно-отправитель:
`unpack` (`workbench/protocol.ts`) четвёртым аргументом берёт ожидаемое окно и
режет всё остальное. До DS-148 этой проверки не было, и док на Pagination
показывал случаи Tree — то есть замер выглядел правдоподобно ровно там, где был
неверен. Перезагружать верстак перед обходом больше не нужно; если вдруг док
опять показывает чужое, сломана проверка, а не приём.

## Числа гейта и числа кадра не сходятся ПО ПОСТРОЕНИЮ

Числа гейта и числа кадра верстака по величине не сходятся ПО ПОСТРОЕНИЮ:
у `.wbf-host` паддинг `30px` на сторону (`workbench/frame.css`, литерал, не
от шкалы), контейнер компонента равен кадру минус 60, а гейт ставит хост ровно
в кадр. (Хендофф 15.09 записал «`1rem * --wbf-z`, 20 px при шкале 1» — это
правило `.wbf-empty`, а не хоста; сверено с исходником.) Сходиться обязаны
механизм и знак, не число.

Минус 60 — только пока у документа кадра нет вертикальной полосы: при
содержимом выше кадра полоса (15 px) молча отнимает свою ширину, и на кадре 440
контейнер 365. Тулбар оболочки печатает это число сам — «контейнер N» и
«полоса −N» рядом с фактическим размером (DS-314); читать его, а не
считать в уме.

Параметр `p.width` в адресе кадра молча игнорируется — это не крутилка.

## Переписанный целиком файл оставляет ПУСТОЙ модуль в кэше vite

**A file rewritten whole leaves an EMPTY module in the vite cache, and the page
blames the importer.** The workbench is a permanent service (`ds-workbench`,
port 5274), and a full-file rewrite — not a patch — while it is up can be read
mid-write: the transform is cached at zero length. The page then fails with
`SyntaxError: The requested module '/protocol.ts' does not provide an export
named 'pack'`, which points at the file that IMPORTS the module, not at the
cache, and the module on disk is perfectly fine. `tsc` and vitest see the disk
and stay green, so nothing else contradicts the browser. Confirm with the size,
not the source, and with the PATH THE SERVER USES: vite's root is `workbench/`,
so a file under it is `/dock.tsx`, and a file outside it goes through `/@fs`
with the absolute path:

```bash
curl -s -o /dev/null -w '%{size_download} %{content_type}\n' http://localhost:5274/dock.tsx
curl -s -o /dev/null -w '%{size_download} %{content_type}\n' "http://localhost:5274/@fs$PWD/src/internal/roving.ts"
```

Zero with `text/javascript` means the cache, not the code. A repository path
(`/workbench/dock.tsx`, `/src/…`) is answered with the SPA fallback — 563 bytes
of `text/html`, the same for every file — and reads as "cache is fine" or "cache
is broken" depending on the eye, while measuring nothing (caught 07.09.2026: six
files, six identical 563s). Cure is `touch` on every file you rewrote.

React state also does not land in the DOM synchronously: read `aria-*` in the
same `evaluate` that dispatched the event and you read the value from BEFORE
it. Wait two frames, or read in a separate call.

## Ввод может не доставляться, и об этом ничто не сообщит

**Ввод может не доставляться, и об этом ничто не сообщит.** Скриншоты,
навигация и JS работают, а клики, клавиши и колесо во вкладку не приходят —
поймано 03.09.2026 на повторном обходе волны 3. Всё, что «не сработало»,
выглядит тогда дефектом компонента. Прежде чем делать ЛЮБОЙ вывод про
клавиатуру или колесо, навесь в странице `click`/`keydown`/`wheel` и убедись,
что после нажатия массив непуст. Если пуст — вывод снимается событиями и
состоянием DOM, и в замечании это говорится прямо: косвенное подтверждение не
выдаётся за прямое.

## Клик пришёл ≠ клик попал: координаты `computer` сжаты

**И пришедшее событие ещё не значит, что клик попал: координаты `computer`
сжаты относительно CSS-пикселей страницы.** Поймано 14.09.2026 на приёмке
DS-149: окно `innerWidth` 3339 CSS px, кадр снимка ~1568 px, коэффициент
2.13. Клик по CSS-координате центра кнопки (328,154) ушёл в CSS-точку
(698,328) — мимо кадра, слушатель в кадре пуст, и это выглядело РОВНО как
«ввод не доставляется». Различает слушатель на ВЕРХНЕМ документе с
`clientX/clientY`: событие пришло, но не туда. **Перед выводом про ввод мерить,
КУДА попал клик, а не только пришёл ли он**; координаты для `computer` —
CSS-координаты, делённые на `innerWidth / ширина ОБЪЯВЛЕННОГО кадра` (инструмент
называет «coordinate frame»; ширина картинки при `scale` в формулу не входит —
приёмка DS-311 получила 2.66 вместо 1.065). Регионы `zoom`
живут в той же сжатой системе.
