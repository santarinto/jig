# Changelog

Все заметные изменения jig (`@santarinto/jig`). Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Уровень выпуска считает компоненты каталога, а не совместимость: удалён компонент — major, добавлен — minor, всё прочее — patch.

## [Unreleased]

### Добавилось

- **Лицензия: jig распространяется под MIT, шрифты — под SIL OFL 1.1 со своими
  текстами** (JIG-33). В 1.0.0 лицензии не было вовсе, то есть юридически «все
  права защищены», а шрифты Inter и JetBrains Mono ехали в `dist/fonts/` без
  текста OFL, которого их лицензия требует. Теперь в тарболе лежит `LICENSE`
  (MIT), в `package.json` стоит `"license": "MIT"`, а рядом со шрифтами —
  `dist/fonts/OFL-Inter.txt` и `dist/fonts/OFL-JetBrainsMono.txt`.

  В вашем коде искать нечего: API, стили и сами файлы шрифтов те же. Если вы
  копируете `dist/fonts/` к себе отдельно от пакета, забирайте оба `.txt`
  вместе со шрифтами: OFL требует распространять их рядом. Такое копирование
  находит команда ниже.

  ```bash
  git grep -n "dist/fonts"
  git grep -l "ds-1c-taxi"   # якорь
  ```

  Код возврата: `1` — честный ноль (шрифты вы берёте из пакета, делать ничего
  не нужно), `0` — нашлось, посмотреть, копируются ли `.txt`; `128` — вызов
  вне репозитория, `129` — битый флаг, прочее — сломан вызов, а не чист код.

### Видимо меняется без ошибки

- **Строка формы переносит подпись наверх раньше: порог `FormRow` поднят с
  `18.6em` до `24em`** (JIG-37). Было так: подпись вставала сбоку, даже когда
  полю оставалось меньше ширины самой подписи. На шкале 1.5 поле получало
  ~163 px при колонке подписи 210, дата «17.03.2026» не влезала, название
  организации резалось многоточием. Теперь, если строка формы (`.ds-formrow`,
  сама строка, а не страница) уже `24em`, подпись стоит над полем.

  Меняется только видимая раскладка: ни ошибки компиляции, ни исключения.
  Затронуты строки шириной от 260.4 до 336 px на шкале 1 — у вас умножьте на
  свою `--ds-ui-scale`: при 1.15 это 299.5…386.4 px. Такие строки раньше
  стояли «подпись слева, поле справа», теперь «подпись сверху, поле во всю
  ширину». Строки шире и уже этого диапазона не меняются. Команда находит
  ваши формы и вашу шкалу:

  ```bash
  git grep -n "FormRow\|\.ds-formrow"
  git grep -n "ds-ui-scale"
  git grep -l "ds-1c-taxi"   # якорь
  ```

  Код возврата: `1` — честный ноль (форм нет; для шкалы — значит 1), `0` —
  найдено, посмотреть строки в узких колонках и панелях; `128` — вызов вне
  репозитория, `129` — битый флаг, прочее — сломан вызов, а не чист код.
  Ноль любой из первых двух команд что-то значит только при ненулевом якоре.

  Ноль любой из первых двух команд что-то значит только при ненулевом якоре.

## [1.0.0] — 2026-09-24

**Первый выпуск jig.** Система та же — 68 компонентов, каталог не менялся с
4.2.6, — меняются имя, место и канал установки. Номер начат заново: уровень
выпуска по-прежнему считает компоненты, а не зрелость, и 1.0.0 — это «первый
выпуск под этим именем», а не «теперь готово». Выпуски до 1.0.0 (пакет
`ds-1c-taxi`, 1.x–4.2.6) описаны в прежнем репозитории и сюда не перенесены;
ниже — всё, что изменилось ПОСЛЕ 4.2.6. Переезжаете с более старой версии —
сперва пройдите пункты до 4.2.6 включительно по прежнему журналу.

**Как читать команды этого выпуска.** Все запускаются от корня ВАШЕГО
репозитория через `git grep`: путь не зашит, а в `node_modules`, где лежит и сам
этот пакет, `git grep` не смотрит. Рядом с каждым искомым — **якорь**: тот же
вызов с прежним именем пакета, которое у переезжающего потребителя обязано
найтись. Код возврата: `1` — честный ноль, `0` — найдено, всё остальное (`128`
вне репозитория, `129` битый флаг) — сломан вызов, а не чист код.

```bash
git grep -l "ds-1c-taxi"           # якорь выпуска: обязан найтись, иначе вы не в том дереве
```

### Breaking

- **Канал установки: тарбол из GitHub Release вместо git-пина** (JIG-28,
  JIG-3). Прежняя строка в `dependencies` — git-адрес с тегом на gitflic;
  новая:

  ```json
  "@santarinto/jig": "https://github.com/santarinto/jig/releases/download/v1.0.0/santarinto-jig-1.0.0.tgz"
  ```

  Пакет собран заранее: при установке ничего не собирается и `devDependencies`
  не качаются. Репозиторий публичный — ключи и токены не нужны. Пин прежний по
  смыслу, точная версия; лок пишет `integrity`, и подменённый ассет даёт
  громкий `EINTEGRITY`, а не другую сборку. Номер 1.0.0 меньше 4.2.6 — для
  зависимости по URL npm версии не сравнивает, `npm install` перепишет лок.
  Пока старый адрес жив, он продолжает ставить 4.x молча — поэтому ищите его
  сами, а не ждите ошибки:

  ```bash
  git grep -n "gitflic"        # точный адрес: прежняя строка установки
  git grep -l "ds-1c-taxi"     # якорь
  ```

- **Действие стало ОДНИМ типом: `ActionBase` вместо четырёх независимых наборов
  полей** (DS-358). В 4.2.6 «кнопка с иконкой, подписью и обработчиком»
  была объявлена четыре раза: `RowAction` (действие строки таблицы), `CardTool`
  (инструмент в шапке `Card`), `CommandAction` (`CommandBar` и `AppBar`),
  `DropdownAction` (пункт `DropdownMenu`). Подпись звалась `label` у трёх и
  `ariaLabel` у четвёртого; обработчик — `onClick` у двух и `onSelect` у двух;
  `id` был у двоих из четырёх. Теперь ядро одно — `id`, `label`, `icon?`,
  `tone?`, `disabled?`, `onSelect?` — и у каждого места своё сужение от него.
  `ActionBase` и `ActionTone` экспортируются из корня пакета.

  Ломается три вещи, и все три — ОШИБКА КОМПИЛЯЦИИ, а не деградация. Тексты
  сняты запуском `tsc` на 4.3.0, а не вспомнены.

  1. **`CardTool.ariaLabel` → `label`.** `error TS2353: Object literal may only
     specify known properties, and 'ariaLabel' does not exist in type
     'CardTool'`.
  2. **`CardTool.onClick` и `RowAction.onClick` → `onSelect`.** `error TS2353:
     Object literal may only specify known properties, and 'onClick' does not
     exist in type 'CardTool'` — и он же с `'RowAction'` в конце. Переименование
     не косметическое: половина мест активируется не мышью (пункт меню с
     клавиатуры, свёрнутое в «Ещё» действие полосы), и `onClick` называл
     устройство ввода вместо события. Обязательность поля НЕ ослаблена: `onClick`
     был обязателен у обоих, `onSelect` обязателен у обоих.
  3. **`id` стал обязательным у `RowAction` и `DropdownAction`** (у `CardTool` и
     `CommandAction` он был и раньше). Ключом списка был индекс массива, а он
     меняется, когда действие скрыли по правам. Текст ошибки РАЗНЫЙ у разных
     мест, и искать надо оба:

     ```
     error TS2322: Type '{ icon: null; label: string; onSelect: () => void; }'
       is not assignable to type 'RowAction'.
       Property 'id' is missing … but required in type 'Omit<ActionBase, "label">'.
     ```

     ```
     error TS2741: Property 'id' is missing in type
       '{ label: string; onSelect: () => void; }'
       but required in type 'ActionBase'.
     ```

     Первый — у `RowAction` и `CardTool`: они объявлены через `Omit`, и `tsc`
     называет в сообщении именно `Omit<…>`, а не `ActionBase` (у `CardTool` там
     будет `Omit<ActionBase, "label" | "tone">`). Второй — у `DropdownAction`,
     который и есть ядро. Искать по `ActionBase` одному значит пропустить
     половину.

  У кого на пути `any` (динамически собранный массив действий, данные из
  бэкенда, `as any` в обёртке) — типа нет, и вместо тихой деградации стоит
  БРОСОК (`TypeError`) с новым именем поля прямо в тексте: «Card: `tools`: поле
  ariaLabel у действия отменено (DS-358) — подпись зовётся label, как у
  действий полосы, меню и строки таблицы. Переименуйте ariaLabel в label.»
  Без него старый вызов нарисовал бы ряд безымянных кнопок, которые ничего не
  делают по нажатию, и ни одной ошибки ни в сборке, ни в консоли.

  ```bash
  git grep -n "ariaLabel"        # верхняя граница по пункту 1: см. оговорку ниже
  git grep -n "onClick:"         # пункт 2: поле объекта, а не атрибут JSX
  git grep -n "tools={"          # адрес: каждый вызов Card с инструментами
  git grep -nE "actions: *\("    # адрес: каждая колонка действий таблицы
  git grep -n "<DropdownMenu"    # адрес: каждое меню
  git grep -l "ds-1c-taxi"       # якорь
  ```

  Коды возврата: `1` — честный ноль, `0` — найдено, прочее (`128` вне
  репозитория, `129` битый флаг) значит сломанный вызов, а не чистый код.

  **Два счёта из шести — ВЕРХНЯЯ ГРАНИЦА, а не класс, и вот почему.**
  `ariaLabel` — ЗАКОННОЕ имя пропа у `LineChart`, `BarChart`, `DonutChart`,
  `ProgressBar`, `RouteBar` и у самого `DropdownMenu`; отменено оно только
  внутри `tools`. Отличить одно от другого `grep`-ом нельзя — поле лежит внутри
  массива, на своей строке, и от объявления `ariaLabel="…"` его отделяет только
  то, в каком объекте оно стоит. Пересечение с `git grep -n "tools={"` и есть
  настоящий список. То же с `onClick:`: двоеточие отсекает обычные кнопки
  (`onClick={…}` — атрибут JSX, в счёт не попадает), но любое ПОЛЕ объекта с
  таким именем в вашем коде попадёт.

  **Пункт 3 `grep`-ом не меряется вовсе, и это не оговорка, а свойство
  предмета: искать нечего — поле ОТСУТСТВУЕТ.** Команды `tools={`, `actions: (`
  и `<DropdownMenu` дают верхнюю границу мест, которые надо открыть глазами; в
  каждом объекте массива обязан появиться `id`. Что покажется вместо адреса —
  названо выше: `TS2322`/`TS2741` при сборке, бросок под `any`.

  Команды прогнаны на фикстуре из двух вызовов — у одного поля стоят на
  ОТДЕЛЬНЫХ строках, у другого того же нет вовсе, — и различают состояния:
  каждая печатает первый вызов и молчит о втором. Измеренное на ней:
  `git grep -n "onClick"` без двоеточия даёт 3 попадания на 2 настоящих (третье
  — обычная `<button onClick={…}>`), `git grep -n "onClick:"` — ровно 2.

  **`grep -r` вместо `git grep` брать НЕЛЬЗЯ**: он заглянет в `node_modules`,
  где лежит сам этот пакет, и посчитает наши `.d.ts` за ваши вызовы. Замерено
  на живом дереве потребителя (первый потребитель, 4.2.6): `git grep -l
  "ariaLabel"` — 4 файла, `grep -rl "ariaLabel" .` — 44, и 20 из разницы лежат
  внутри `node_modules/ds-1c-taxi/`, начиная с
  `node_modules/ds-1c-taxi/dist/src/components/DropdownMenu/DropdownMenu.d.ts`.
  Одиннадцатикратный перебор на команде, которая выглядит той же самой.

  Что чинится механически:
  - в каждом объекте `tools={[…]}`: `ariaLabel:` → `label:`, `onClick:` →
    `onSelect:`, добавить `id:`;
  - в каждом объекте, который возвращает `actions: (row) => […]`: `onClick:` →
    `onSelect:`, добавить `id:`;
  - в каждом пункте `items` у `DropdownMenu`: добавить `id:`. Разделитель
    (`{ separator: true }`) остаётся как был — он не действие.

- **`DropdownMenu.trigger` — теперь ЭЛЕМЕНТ-КНОПКА, а не узел внутри нашей
  обёртки** (DS-359). В 4.2.6 компонент оборачивал переданное в свою
  кнопку `.ds-dropdown__triggerwrap`, поэтому в `trigger` полагалось класть
  НЕинтерактивный узел — настоящая кнопка дала бы `<button><button>`. Теперь
  пропы навешиваются прямо на ваш элемент через `cloneElement`, как это с 4.0
  делает `Popover`, а обёртки нет вовсе. Тип пропа изменился с
  `React.ReactNode` на `React.ReactElement<Partial<DropdownMenuTriggerProps>>`;
  сам `DropdownMenuTriggerProps` экспортируется из корня пакета.

  **Ломается ЧЕТЫРЬМЯ способами, и три из них компилятор не видит.**

  1. **`<span>` в `trigger`** — форма, которой учило наше же превью. Не ошибка
     типа: `<span>` и `<button>` оба `ReactElement`, TypeScript их не
     различает. Бросает.
  2. **Фрагмент** (`trigger={<>Текст <Icon/></>}`). Тоже не ошибка типа.
     Бросает.
  3. **Ложный `trigger`** (`trigger={cond && <X/>}` при ложном `cond`). В 4.2.6
     это молча давало встроенный кебаб — законный способ «иногда свой триггер,
     иногда системный». Теперь запрещено типом, а под `any` бросает. Замена:
     `trigger={cond ? <Button>…</Button> : undefined}`.
  4. **Строка или число** (`trigger="Ещё"`). Единственная форма, которую ловит
     компилятор:

     ```
     error TS2322: Type 'string' is not assignable to type
       'ReactElement<Partial<DropdownMenuTriggerProps>, string | JSXElementConstructor<any>>'.
     ```

  **ГДЕ ПРИЗЕМЛЯЕТСЯ БРОСОК — это не строка в консоли.** Он стоит в ФАЗЕ
  РЕНДЕРА, а не в эффекте (в эффекте на сервере проверки не было бы вовсе). У
  SSR это падение рендера страницы, то есть 500; у CSR — ближайший error
  boundary, а если его нет, размонтирование дерева, то есть белый экран.
  Апгрейд без прогона страницы с меню не годится: экран будет пустым, а не
  «почти работающим».

  Тексты сняты запуском на 4.3.0 и приведены дословно.

  `<span>` (и любой другой отвергнутый интринсик — подставляется его тег):

  > DropdownMenu: `trigger`: триггер — ЭЛЕМЕНТ-КНОПКА, а пришёл `<span>`
  > (DS-359). Компонент не оборачивает переданное в свою кнопку —
  > обработчик и `aria-*` он вешает прямо на этот элемент. `<span>` не
  > фокусируется, не объявляется кнопкой и с клавиатуры оверлей не открывает.
  > Список закрыт: законны только `<button>` и `<a href>`, а `<input
  > type="button">`, `<summary>`, `<label>` и пользовательский элемент
  > (`<my-button>`) отказывают наравне со `<span>` — их модель ввода принадлежит
  > им, а не оверлею. Передайте `<Button>`, `<button>` или `<a href>` — либо свой
  > компонент-обёртку кнопки: `trigger={<Button
  > variant="secondary">Действия</Button>}`.

  Фрагмент:

  > DropdownMenu: `trigger`: триггер — ОДИН элемент-кнопка, а не фрагмент
  > (DS-359). `<>…</>` пропов не принимает вовсе: `onClick` и
  > `aria-expanded` уехали бы в никуда, а React напечатал бы предупреждение и
  > продолжил рисовать. Передайте `<Button>`, `<button>` или `<a href>` — либо
  > свой компонент-обёртку кнопки: …

  Ложное значение (`null`, `false`, `''` — подставляется пришедшее):

  > DropdownMenu: `trigger`: пришло `null` (DS-359). Ложное значение
  > больше не означает «встань встроенным кебабом» — до 4.3.0 `trigger={cond &&
  > <X/>}` молча давал кебаб, и отличить это от забытого триггера было нельзя.
  > Нет триггера — передайте `undefined` или не передавайте проп вовсе: встанет
  > встроенный кебаб «⋯». Условный триггер пишется `trigger={cond ? <Button>…
  > </Button> : undefined}`.

  `<a>` без `href`:

  > DropdownMenu: `trigger`: триггер `<a>` без `href` (DS-359) — такая
  > ссылка не фокусируется, то есть это тот же `<span>`, только на вид. …

  Строка (эта форма ловится и компилятором, см. TS2322 выше):

  > DropdownMenu: `trigger`: триггер — ЭЛЕМЕНТ-КНОПКА, а не string
  > (DS-359). Компонент не оборачивает переданное в свою кнопку —
  > обработчик и `aria-*` он вешает прямо на этот элемент. …

  **Список ИНТРИНСИКОВ ЗАКРЫТ:** законны `<button>` и `<a href>`. `<input
  type="button">`, `<summary>`, `<label>`, пользовательский элемент
  (`<my-button>`) отказывают наравне со `<span>` — они фокусируемы, но их
  модель ввода принадлежит им, а не меню. Выход для всех них один и он назван в

### Добавилось

- **`Button` получил именованные слоты `icon?: ReactNode` и `iconEnd?: ReactNode`.**
  Рисуются внутри `.ds-btn__label` по краям: иконка — подпись — `iconEnd`.
  Оба декоративны (`aria-hidden`) и проходят через системный `<Icon>` — та же
  нормализация чужого SVG, что у остальных значков системы, а не голый
  `ReactNode`, который приезжает со своей толщиной штриха и размером.

  ```tsx
  <Button icon={<IconPlus />}>Создать</Button>
  <Button iconEnd={<IconChevronDown />}>Ещё</Button>
  ```

  Безымянный `child` продолжает работать без изменений — `Button` по-прежнему
  принимает произвольное содержимое, и ничего у существующих вызовов не ломает.

  **`iconOnly` спорит за содержимое кнопки, если занять сразу оба слота —
  это `TypeError` в рантайме, а не молчаливая деградация:**
  - `iconOnly` + `iconEnd` — throw ВСЕГДА: у кнопки из одной иконки нет
    «конца», второго края подписи не бывает.
  - `iconOnly` + `icon` + `children` разом — throw: два претендента на одно
    место, `icon` сам есть содержимое такой кнопки.
  - `iconOnly` + `icon` БЕЗ `children` — законно, новая форма: `icon` и есть
    содержимое.
  - `iconOnly` + `children` БЕЗ `icon` — законно и не меняется: старая форма
    (иконка одиночным `children`) продолжает работать как раньше.

  Обе запрещённые комбинации отражены и в типах `ButtonProps` — там, где форма
  union позволяла это без цены существующим вызовам.

  Слот занят, только если React что-то рисует: `icon={cond && <IconPlus />}`
  при ложном `cond` не рисует пустого значка и не считается занятым в проверках
  `iconOnly` — рядовой идиом условной иконки работает без побочных эффектов.

- **`FormTab` получил два необязательных поля: `icon` и `modified`**
  (DS-363). До этого вкладка открытой формы умела только подпись, хотя
  соседний `Tabs` умел значок с 4.0 — система расходилась сама с собой на двух
  компонентах, стоящих рядом на одном экране.

  ```ts
  interface FormTab {
    id: string
    label: string
    disabled?: boolean
    icon?: React.ReactNode   // новое
    modified?: boolean       // новое
  }
  ```

  **`icon` — тип документа, не его состояние.** Значок встаёт перед подписью,
  декоративен (`aria-hidden`), цвет наследует от подписи. Форма та же, что у
  `Tabs.icon`, намеренно: одно понятие — одно имя и одна форма, второй мы не
  заводим.

  **`modified` — «форма открыта и не записана».** Система рисует её сама:
  знак `*` суффиксом после подписи плюс слово «Не записано» в `title` вкладки.
  Знак — символ, а не цвет и не заливка; цвет в этом не участвует вовсе.

  Отдельным полем, а не картинкой в `icon`, по расчёту: состояние документа
  одинаково у ВСЕХ, кто показывает полосу открытых форм, а незакодированное
  состояние каждый закодирует по-своему — чаще всего цветным кружком, то есть
  цветом в одиночку, что система запрещает. Кладя `*` в `icon` руками, вы
  получите тот же знак без слова и без гарантии, что он переживёт смену темы.

  **`label` осталось `string`, и это решение, а не недоделка.** Расширить его
  до `ReactNode` было бы естественным ходом — и оно ломает подсказку крестика:
  её текст строится как «Закрыть <подпись>» и уезжает в атрибут `title`,
  который принимает строку. Узел там стал бы `[object Object]`. Картинке место
  в `icon`, состоянию — в `modified`, подписи — в подписи.

  Ошибки компиляции правка не даёт и дать не может: оба поля необязательные,
  старый вызов остаётся верным. Ничего не меняется и на экране, пока вы не
  передадите новое поле.

  Где посмотреть, не пригодится ли:

  ```bash

  git grep -l "ds-1c-taxi"              # якорь: обязан найтись, иначе вы не в том дереве
  ```

  Код возврата: `1` — честный ноль, `0` — найдено, прочее (`128` вне
  репозитория, `129` битый флаг) — сломан вызов, а не чист код.

  Команда проверена РАЗЛИЧЕНИЕМ на фикстуре с раскладкой потребителя:
  многострочный `<FormTabs` (после имени сразу перевод строки) и однострочный

  и `<MyFormTabs/>` не берутся; состояние «полоса не используется» даёт код 1
  при якоре 0.

- **`Badge brand` принимает не только хекс, но и ссылку на категориальный токен
  системы — `var(--ds-chart-N)`, N от 1 до 8** (DS-371). Ошибки
  компиляции правка не даёт и дать не может: тип пропа как был `string`, так и
  остался, расширилось то, что компонент СЧИТАЕТ цветом.

  **Зачем.** `ToggleGroup variant="swatch"` — тот виджет, которым вы даёте
  пользователю ВЫБРАТЬ цвет метки, — с 4.2.3 документирован так: «цвет плашки,
  ожидается `var(--ds-chart-N)`». А `Badge`, которым эта метка потом рисуется,
  принимал ТОЛЬКО хекс и всё остальное молча ронял в `neutral`. Два конца одного
  потока расходились о том, что такое цвет: выбираете токеном, показываете
  хексом.

  Довод, на котором `brand` держал «только хекс», был «в базе цвет лежит
  хексом». Он перестал быть верным у потребителя раньше, чем у нас: цвет,
  привязанный к теме, хексом не выражается — хекс есть значение ОДНОЙ темы, и на
  переключении она уезжает.

  ```tsx
  <Badge brand="var(--ds-chart-3)">{tag.name}</Badge>
  ```

  Если в вашей базе лежит короткое имя (`chart-3`), подставьте его сами —
  одной строкой у себя:


  Произвольный `var()` тоже не принимается: компонент выводит из одного значения
  ДВА цвета и отвечает за их контраст, а чего он проверить не может, то и не
  берёт.

  **Мусор по-прежнему даёт штатный `neutral`**, а не сломанный бейдж: пустая
  строка, `null` из базы, `var(--ds-chart-9)`, `var(--ваш-токен)`, `c026d3` без

  отсутствие класса.

  Вместе с `tone` — по-прежнему БРОСОК, теперь и с токеном: это два разных

  Читаемость обоих выведенных цветов на всех восьми токенах проверена замером в
  браузере, на трёх подложках (`--ds-surface`, `--ds-surface-subtle`,

  ```bash
  git grep -n "brand="               # где передаётся цвет — ВЕРХНЯЯ граница, проп есть не только у нас
  git grep -l "ds-1c-taxi"           # якорь: обязан найтись, иначе вы не в том дереве
  ```

- **Документация `useAnchoredPosition` ошибочно называла `contain: paint`
  безопасным для `Popover`/`DropdownMenu`/`Tooltip`/флаута `SideNav` — это
  было неверно** (DS-357). Было (v4.2.6,
  `dist/src/internal/useAnchoredPosition.d.ts`): «`contain: paint` ловушкой не
  оказался (расхождение 0)». Перемер chromium 149.0.7827.55 (чистый лист,
  предок `position: static` со смещением через `margin`, узел `position:
  fixed` и отдельно `position: absolute` внутри) показывает обратное:
  `contain: paint|layout|strict|content` уводит ОБА в коробку предка — точно
  так же, как `transform`, `filter`, `backdrop-filter`, `perspective`,
  `will-change: transform`. Прежний «0» объясняется методологически: замер
  снимался на предке, стоящем в начале вьюпорта, где ловушка и её отсутствие
  дают одинаковое число — смещаться было некуда в обоих случаях.

  Поведение компонентов НЕ менялось — это правка комментария/документации.
  Но если вы ставили `contain: paint` (или `layout`/`strict`/`content`) на
  обёртку, внутри которой лежит один из этих компонентов (`Popover`,
  `DropdownMenu`, `Tooltip`, `Select`-подобные с флаутом, а также `Combobox`/
  `DatePicker`, использующие тот же механизм), полагаясь на прежнее
  «безопасно», — позиция плавающей панели у вас может быть неверной.
  `container-type` (контейнерные запросы) и голый `contain: size` — БЕЗ
  ИЗМЕНЕНИЙ, они и раньше, и сейчас не ловушка.

  Команда даёт НИЖНЮЮ ГРАНИЦУ, а не точный счёт: однострочную декларацию
  `contain: paint;` она ловит, а форму со значением на отдельной строке
  (`contain:\n  paint;`) — нет. Проверено различением на фикстуре: первая
  форма даёт код `0`, вторая — ложный `1` (проверял многострочную декларацию
  отдельно, редкий случай, но грепом не различим). Нашедшийся `contain:` сам
  по себе не дефект — дефект в том, что он оборачивает один из перечисленных
  компонентов; это решает глаз, не grep.

  ```bash
  git grep -nE "contain\s*:\s*[^;]*\b(layout|paint|strict|content)\b" -- '*.css' '*.scss'
  git grep -l "ds-1c-taxi"   # якорь
  ```

  Код возврата: `1` — честный ноль (учти ограничение про многострочную форму
  выше), `0` — нашлось, смотреть глазами, не оборачивает ли узел один из
  четырёх компонентов; `128` — вне репозитория, `129` — битый флаг, прочее —
  сломан вызов, а не чист код.

- **`Popover`, `DropdownMenu`, `Tooltip` и всплывающее свёрнутой `SideNav`
  вставали НЕ У СВОЕЙ КНОПКИ, если над ними в вашей разметке был предок с
  `transform`, `filter`, `backdrop-filter`, `perspective`,
  `will-change: transform` или `contain: layout|paint|strict|content`**
  (DS-367). Было (v4.2.6): такой предок становится containing block для
  `position: fixed`, и панель уезжала ровно на его смещение во вьюпорте —
  замерено на предке со сдвигом 120/120 px, панель уехала на 120,120. Стало:
  начало коробки предка измеряется и вычитается, панель встаёт у кнопки
  независимо от того, во что вы её обернули.

  Это ВИДИМОЕ ИЗМЕНЕНИЕ БЕЗ ОШИБКИ КОМПИЛЯЦИИ: ни один вызов не ломается, но
  если вы обходили дефект руками — своим `margin`/`translate` на панели, своим
  `position`, перенесённым узлом — обход теперь СДВИНЕТ панель второй раз, уже
  в другую сторону. Поэтому команда ищет не наши имена, а ваши предки-ловушки:
  места, где поведение изменилось, — это они.

  Команда ищет ОБЪЯВЛЕНИЯ, а не оборачивание: найденная строка не дефект сама
  по себе, дефект был только там, где такой предок стоял НАД одним из четырёх
  компонентов, — это решает глаз, не grep. Верхняя граница, а не точный счёт.
  Пределы, проверенные на фикстуре из двух деревьев: `text-transform`,
  `contain: size`, `container-type` и `will-change: opacity` НЕ считаются
  (containing block они не создают) — на чистом дереве команда даёт честный
  `1`; многострочная декларация ловится по имени свойства (`transform:` на
  своей строке найдётся), а вот `contain:` со значением на следующей строке —
  нет; `filter: none` и `transform: none` попадут в список ложно.

  ```bash
  git grep -nE "(^|[^-a-zA-Z])(transform|filter|backdrop-filter|perspective)[[:space:]]*:|(^|[^-a-zA-Z])will-change[[:space:]]*:[^;]*(transform|filter|perspective)|(^|[^-a-zA-Z])contain[[:space:]]*:[^;]*(layout|paint|strict|content)" -- ':!node_modules'
  git grep -l "ds-1c-taxi"   # якорь
  ```

  Код возврата: `1` — честный ноль (ловушек нет, поведение у вас не менялось),
  `0` — нашлось, смотреть глазами, не оборачивает ли эта строка `Popover`,
  `DropdownMenu`, `Tooltip` или `SideNav`; `128` — вызов сделан вне
  репозитория, `129` — битый флаг, прочее — сломан вызов, а не чист код.
  `':!node_modules'` в команде не украшение: без него в счёт попадает сам
  установленный пакет.

  Чего исправление НЕ чинит и не может: предок с `contain: paint` или с
  не-`visible` `overflow` по-прежнему ОБРЕЖЕТ панель, вставшую верно, а
  ширина панели `auto` по-прежнему считается от коробки предка, а не от
  экрана, — то есть под узким предком текст переносится иначе. Оба лечатся
  только порталом, от которого система отказалась осознанно (причина — в
  докблоке `useAnchoredPosition.ts`).

- **`Popover`, `DropdownMenu`, `Tooltip` и всплывающее свёрнутой `SideNav`
  переставляются, когда панель или кнопка меняют РАЗМЕР, а не только при
  прокрутке и ресайзе окна** (JIG-7). В 4.2.6 положение считалось один раз при
  открытии и потом только по `scroll` и `resize`. Если панель вырастала уже
  открытой (догрузился шрифт, пришло асинхронное содержимое, предок сменил
  `--ds-ui-scale`), она оставалась на месте, посчитанном по старой высоте.
  У `placement="top-*"` это значит, что панель наезжает на свою же кнопку.
  Замерено на шкале 1.15: высота при замере 63.8 px, после отрисовки 85.5 px,
  в результате кнопка закрыта на 19 px и по ней не попасть кликом. Теперь за
  размером панели и кнопки следит `ResizeObserver`, и панель встаёт на зазор
  `--ds-anchor-gap` от кнопки.

  Поведение меняется видимо, но без ошибки, и следа в вашем коде у изменения
  нет: вызовы те же, искать нечего. Заметить можно одно: если вы обходили
  застывшую панель руками, например посылали `window.dispatchEvent(new
  Event('resize'))` после загрузки содержимого, такой обход теперь лишний, но
  безвредный.

- **Поле `NumberField` на мелкой шкале стало шире и вмещает четыре цифры с
  кареткой** (JIG-31). В 4.2.6 ширина поля была `3.5rem × --ds-ui-scale` и не
  зависела от шрифта. Цифры на мелком кегле растеризуются относительно шире,
  и после смены базы кегля 13 → 14 на шкале 0.875 поле держало 38.5 px при
  нужных 40: «5000» упиралось в край. На шкале 1 запаса не было совсем (44 при
  44). Теперь ширина — большее из прежней формулы и `5ch` плюс отступы. `ch`
  считается в шрифте самого поля, так что ширина идёт за кеглем.

  Шкала 1 здесь — единица отсчёта. Поле стало шире на 1 px при шкале 1 (56 →
  57) и на 1.5 px при 0.875 (49 → 50.5). При 1.15 и 1.5 ширина прежняя: там
  старая формула и так была больше. Сначала узнай свою шкалу, потом ищи
  вызовы. Заметно это только там, где `NumberField` стоит в ряду с жёстко
  подогнанной суммой ширин.

  ```bash
  git grep -n "ds-ui-scale"
  git grep -l "ds-1c-taxi"           # якорь
  git grep -n "<NumberField"
  git grep -l "ds-1c-taxi"           # якорь
  ```

  Код возврата: `1` — честный ноль, `0` — нашлось; `128` — вызов вне
  репозитория, `129` — битый флаг, прочее — сломан вызов, а не чист код. Ноль
  у первой команды значит «шкала 1» только при ненулевом якоре.
